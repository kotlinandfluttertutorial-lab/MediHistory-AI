# ADR-001 — MVVM with Repository Pattern
**Date:** 2026-10-25  
**Status:** Accepted  
**Deciders:** Engineering team

## Context
The project needs a clear, testable separation of concerns between the UI (Jetpack Compose), business logic, and data access. Without a defined architectural pattern, concerns bleed across layers, making the codebase harder to test and maintain. The team evaluated several Android architecture patterns before project start.

## Decision
Adopt MVVM (Model–View–ViewModel) as the Android application architecture, with:
- Repository interfaces defined in `domain/repository` — ViewModel never imports Room or Retrofit directly.
- Repository implementations in `data/repository` that wire Room DAOs and remote APIs together.
- UseCase classes in `domain/usecase` for operations that a ViewModel would otherwise require more than one repository for.
- ViewModels expose `StateFlow` or `LiveData`; the Compose UI layer only observes state and emits events.

## Consequences
### Positive
- Clear single-responsibility separation: UI, ViewModel, domain, data.
- ViewModels and UseCases are independently unit-testable with fake repositories.
- Repository interfaces decouple the domain layer from framework implementations (Room, Retrofit).
- Consistent with the Android team's recommended architecture and Jetpack guidance.
- Easy to add or swap data sources behind the repository interface.

### Negative / Trade-offs
- More boilerplate than a single-layer approach (interface + implementation + UseCase for each domain entity).
- UseCase layer adds an extra abstraction that is not always necessary for simple CRUD flows.
- Developers unfamiliar with the pattern need onboarding before contributing.

## Alternatives Considered
| Alternative | Reason rejected |
|---|---|
| MVI (Model–View–Intent) | Higher complexity and steeper learning curve; MVVM is sufficient for this app's interaction patterns and better supported by official Jetpack samples. |
| MVP (Model–View–Presenter) | Does not compose well with Jetpack Compose; presenter lifecycle management adds friction. |
| No formal architecture (procedural) | Untestable, unmaintainable at scale; rejected immediately. |
