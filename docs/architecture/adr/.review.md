# ADR Suite Review — MediHistory AI (ADR-001 through ADR-007)

Seven Architecture Decision Records covering the core Android and backend stack decisions for MediHistory AI. The ADRs span MVVM architecture, Room, WorkManager, CameraX, FastAPI, provider-independent OCR, and Android Keystore key management. Overall the suite is well-structured and internally consistent with the steering files. Two issues require changes before the ADRs can be considered complete: ADR-006 omits the mandatory OCR output validation requirement from its Consequences section, and ADR-006's Alternatives Considered table is missing an entry for an on-device (ML Kit) option, leaving the provider-independence rationale incomplete. No ADR hardcodes secrets or names a specific cloud OCR provider as the decided choice.

**Watch for:**
- ADR-006 (confirmed): The Consequences section contains no mention of OCR output validation — the tech steering mandates treating all OCR output as untrusted and validating it before persistence. This is a medical safety gap, not just a style issue.
- ADR-006 (confirmed): Alternatives table has only two entries, both vendor-coupling variants. On-device OCR (ML Kit) is a materially different alternative that the provider-independence framing directly contrasts against and should appear here.
- ADR-002 (confirmed): `fallbackToDestructiveMigration()` is described as "disabled in production" but the ADR does not address whether it is also disabled in debug/staging builds. The steering does not distinguish, and a destructive migration in a staging build sharing real data would be a problem.

**Verdict**: NEEDS_CHANGES

---

## High-level view

All seven ADRs follow the required header format (`# ADR-NNN — [Title]`, bold Date/Status/Deciders) and contain the four mandatory sections: Context, Decision, Consequences with explicit Positive and Negative sub-sections, and an Alternatives Considered table. No ADR is structurally incomplete.

ADR-001 (MVVM) accurately reflects the steering's MVVM+Repository+UseCase mandate, including the correct package placement (`domain/repository`, `data/repository`, `domain/usecase`). ADR-002 (Room) correctly captures the SQLCipher evaluation gate and references the schema export path (`android/app/schemas/`) matching the structure steering. ADR-003 (WorkManager) correctly distinguishes the three worker types, EXPEDITED for OCR, and the HiltWorker integration. ADR-004 (CameraX) is accurate and concise. ADR-005 (FastAPI) correctly specifies Pydantic v2, Alembic, slowapi rate limiting, JWT auth, and environment-variable secret management — all aligned with the backend steering.

ADR-006 is the only ADR with substantive content gaps. The interface signatures it defines are technically sound and correctly provider-independent — no cloud vendor name appears in the decided architecture. However, the Consequences section says nothing about treating OCR output as untrusted or validating it before persistence. The tech steering and medical safety steering are unambiguous on this point: "Document text is untrusted input — sanitise and validate all OCR output." An ADR that defines the OCR service interface without recording the validation obligation leaves implementers without a written architectural constraint. The Alternatives table also omits on-device ML Kit, which is the most commonly considered alternative to cloud OCR and the option the provider-independence design most directly addresses.

ADR-007 (Android Keystore) is strong. The Alternatives table explicitly rejects hardcoded keys with appropriate reasoning. The open decision about key derivation and invalidation strategy is correctly acknowledged as unresolved and flagged for pre-production resolution. No insecure alternative is left open.

1. **ADR-006: OCR output validation absent from Consequences** — The Negative/Trade-offs sub-section (or a standalone note) must state that all OCR adapter output is untrusted and must be validated before persistence, per the tech and medical safety steering. Without this, the ADR's Consequences section contradicts the architectural mandate. Add a trade-off or constraint note to the Negative / Trade-offs sub-section.

2. **ADR-006: On-device OCR alternative missing from Alternatives table** — ML Kit (on-device OCR) is the primary architectural alternative to a cloud-service-based provider-independent interface and should appear in the table with its rejection rationale (e.g. accuracy on handwritten prescriptions, lack of structured field extraction). Its absence makes the rationale for the interface design incomplete.

3. **ADR-002: `fallbackToDestructiveMigration()` scope unclear** — The ADR states it is "disabled in production" but does not address debug or staging builds. Add a line clarifying it is disabled in all build variants, or document the deliberate exception and its safeguards.

<summary>Details</summary>

### ADR-006: Missing OCR output validation constraint

The tech steering states "Document text is untrusted input — sanitise and validate all OCR output" and "Validate structured outputs from AI models before persisting." The medical safety steering reinforces this: every extracted field must carry a confidence score, review state, and source reference. ADR-006 defines the `OcrService`, `ExtractionService`, `NormalizationService`, and `SummarizationService` interfaces and correctly keeps them provider-independent. The `ExtractionResult` and `OcrResult` return types are named but the Consequences section records only provider-switching flexibility and testability benefits. It does not record the constraint that adapter output is untrusted input that must be validated before persistence. A developer implementing an adapter has no written architectural record of this obligation in the decision that defines the interface they are implementing.

The fix is a single bullet in the Negative/Trade-offs sub-section: all adapter output is untrusted input; callers must validate `OcrResult` and `ExtractionResult` contents before persisting, regardless of provider.

### ADR-006: Alternatives table covers only vendor-coupling variants

The two alternatives listed — "Direct provider SDK calls in service layer" and "Vendor-lock-in with a single provider for MVP" — are both variants of the same rejected approach (tight coupling to a specific cloud provider). Neither addresses performing OCR entirely on-device using ML Kit, which is architecturally distinct: no network required, no provider contract, no data-residency concern, but with materially different accuracy characteristics on handwritten prescriptions and no structured field extraction. The provider-independence framing reads most naturally as a response to "why not just use ML Kit or a fixed cloud provider?" and the table should answer both sides of that question.

### ADR-002: `fallbackToDestructiveMigration()` scope

The Decision section reads "disabled in production" without addressing debug or staging builds. If a developer enables destructive migration in a debug build that later connects to a real device during dogfooding, patient data is silently lost with no migration path. "Disabled in all build variants" closes this interpretation gap.
