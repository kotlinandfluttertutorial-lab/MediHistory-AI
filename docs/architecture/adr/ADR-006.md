# ADR-006 — Provider-Independent OCR Service Interface
**Date:** 2026-10-25  
**Status:** Accepted  
**Deciders:** Engineering team

## Context
The app requires OCR and AI text extraction to convert prescription images into structured data. Multiple cloud and on-premise providers exist, each with different APIs, pricing, data-residency characteristics, and availability. Coupling the codebase directly to a single provider's SDK or API surface would make it expensive to switch providers, test the pipeline without live credentials, or comply with future data-residency requirements.

## Decision
Define all AI/OCR capabilities as provider-independent abstract interfaces. No provider-specific imports appear outside adapter classes:
- `OcrService.extract_text(document_bytes: bytes) -> OcrResult`
- `ExtractionService.extract_fields(ocr_text: str, schema: ExtractionSchema) -> ExtractionResult`
- `NormalizationService.normalize_medicine(name: str, brand: str) -> NormalizationResult`
- `SummarizationService.summarize(records: list, schema: SummarySchema) -> SummaryResult`

Concrete adapters (one per provider) implement these interfaces and are injected via configuration. The active adapter is selected at runtime through environment variables — no provider name appears in route or service business logic. This design allows the team to defer the final provider selection until a formal evaluation against cost, accuracy, latency, and data-residency criteria is complete (see open decision AD-004 in `docs/architecture/architecture.md`).

## Consequences
### Positive
- Provider can be swapped by changing configuration, not code.
- Business logic and routes are fully testable with a mock adapter — no live credentials required in CI.
- Data-residency and compliance requirements can be addressed by selecting the appropriate adapter.
- Multiple adapters can coexist, enabling A/B evaluation or regional routing.
- Separates the provider evaluation decision from the architectural decision.

### Negative / Trade-offs
- Adapter abstraction adds a layer of indirection and an extra file per capability per provider.
- Interface design must be stable enough to accommodate all likely providers; provider-specific features (e.g. bounding boxes, page-level confidence) must be exposed through the common schema or lost.
- Team must maintain adapters as provider APIs evolve.

## Alternatives Considered
| Alternative | Reason rejected |
|---|---|
| Direct provider SDK calls in service layer | Tightly couples business logic to a single vendor; switching providers requires changes across multiple files; untestable without live credentials. |
| Vendor-lock-in with a single provider for MVP | Reduces initial effort but creates migration risk if the provider changes pricing, availability, or data-residency terms. |
