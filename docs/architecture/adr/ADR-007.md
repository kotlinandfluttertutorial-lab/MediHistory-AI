# ADR-007 — Android Keystore for Encryption Key Management
**Date:** 2026-10-25  
**Status:** Accepted  
**Deciders:** Engineering team

## Context
The app stores sensitive medical records locally on the device. Encryption keys used to protect this data must themselves be protected from extraction by other apps, from offline attacks if the device is lost, and from memory-scraping attacks. Key management is a security-critical decision that affects the confidentiality of all locally stored patient data.

## Decision
Use the Android Keystore System for all local encryption key generation and storage:
- Keys are generated inside the Keystore and never leave the secure hardware enclave (where supported by the device).
- Keys are referenced by alias; raw key material is not accessible to the application process.
- Keystore-backed keys are used to encrypt/decrypt the local database key (when SQLCipher or equivalent is adopted) and to sign export packages.
- `EncryptedSharedPreferences` (which uses Keystore internally) is used for all sensitive preference values. Plaintext `SharedPreferences` is prohibited for tokens or keys.
- Key derivation and invalidation strategy (e.g. user authentication binding, key rotation on app reinstall) must be formally evaluated and documented before the production data layer is implemented (see open decision AD-001 in `docs/architecture/architecture.md`).

## Consequences
### Positive
- Key material is hardware-backed on devices with a Trusted Execution Environment — extraction is not possible even with root access on those devices.
- No custom key storage code required; Keystore is a standard Android system API.
- Integrates natively with `EncryptedSharedPreferences` and SQLCipher's key-unlock pattern.
- Supports user authentication binding (keys require biometric/PIN unlock), enabling stronger access control.

### Negative / Trade-offs
- Key-backup behaviour must be considered: Keystore keys are not included in Android Auto Backup by default, so a reinstall loses the ability to decrypt data unless a recovery path is designed.
- Hardware-backed Keystore is not available on all devices (older or low-end hardware falls back to software-only).
- SQLCipher and key rotation strategy add implementation complexity that must be resolved before the data layer is built.
- Key invalidation on biometric enrolment changes must be explicitly handled to avoid locked-out users.

## Alternatives Considered
| Alternative | Reason rejected |
|---|---|
| Hardcoded encryption keys | Completely insecure — any attacker with the APK can extract the key. Rejected immediately. |
| User-derived keys only (PBKDF2 from PIN) | Acceptable for some use cases, but PIN changes or forgotten PINs result in data loss unless a recovery path is designed; Keystore is the standard Android solution and should be the primary mechanism. |
| Third-party key vault (e.g. cloud-hosted HSM) | Requires network access to decrypt local data — breaks offline-first requirement. Not suitable as the primary key store. |
